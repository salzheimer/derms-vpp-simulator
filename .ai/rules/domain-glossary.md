# Domain Glossary

- **DER (Distributed Energy Resource)** — a fleet device (battery, solar, EV, wind, etc.) managed by RVA. In the data model, a DER is an `Asset`.
- **Utility-integrated VPP vs. third-party aggregator** — RVA's primary model is utility-integrated: the utility orchestrates enrolled customer DERs for distribution and bulk-system needs. The aggregator model (a non-utility party dispatching within limits set by the utility) is also supported. See `.ai/plans/MASTER_PLAN.md` section 2.
- **Program** — a utility or aggregator offering that customers enroll DERs in. It records its operator, value stream, and settlement rule, so the operating model is chosen per program, not per deployment.
- **Operating envelope** — time-varying import/export limits (kW) for a grid node (by `grid_node_id`) or connection point. Computed by RVA (utility-integrated) or received from a utility DERMS (aggregator). Every dispatch is capped by it. RVA computes it behind one limit-evaluation interface: from static node ratings first, and later from power flow if a digital twin is added, without changing callers.
- **Flexibility commitment** — an obligation to deliver X kW from a portfolio during a time window, created either by a program event or by a market award. Dispatch fulfils commitments; it never exceeds operating envelopes.
- **Asset** — a grid-facing controllable resource: everything behind **one control interface**, at **one connection point** (premise, neighborhood transformer, feeder, or substation), with **one rating at that point**. It is what dispatch sees, and its rating is not the sum of its components (a shared inverter caps PV + battery together). Owned by GridTopology (dual-key: surrogate `long` id + natural `Code`). Other modules refer to it only by `AssetId` or through the `AssetSnapshot` contract. Superseded the earlier battery-specific `BatteryState` model.
- **Asset component** — what an asset is made of (a PV array, battery modules), typed by `TechnologyType` and `HardwareProfile`. Components drive simulation physics and determine an asset's makeup (PV only, storage, PV + storage) and energy capacity. They are never dispatched directly.
- **Hardware profile** — a manufacturer equipment model with per-unit nameplate specs. Energy products (batteries, PV modules) describe components; control equipment (inverters, gateways, plant controllers) is an asset's control profile, whose manufacturer selects the device-integration adapter.
- **Premise** — a customer site behind one utility meter (the point of common coupling), served from a neighborhood transformer (secondary service) or directly from a feeder (primary service, where the customer owns its transformer). Carries the customer segment, service capacity (import limit), site export limit (`0` = non-export), and whether the site can island. A behind-the-meter microgrid is a premise that can island; all assets at a premise island together.
- **Customer segment** — the premise's utility service class (`residential`, `commercial_industrial`). Independent of equipment size: a home with three Powerwalls is still `residential`.
- **Microgrid** — a utility-side grouping spanning several premises and/or feeder-connected assets, connected at a feeder or substation (so always `ftm`). Has its own import/export limits and island capability. Not used for single-site microgrids — those are premises.
- **Site vs. system limits** — site limits apply at the point of common coupling (premise or microgrid); system limits apply at the point of DER connection (asset), following IEEE 1547. Dispatch is capped by the smallest of the system limit, site limit, node ratings, and operating envelope.
- **Islanding** — *intentional* islanding is a capability of a premise or microgrid (backup gateway or microgrid controller plus a grid-forming source); being islanded is runtime state, during which members are unavailable for grid dispatch. *Unintentional* islanding is a safety fault — a DER energizing a de-energized line — that IEEE 1547 requires inverters to stop within 2 seconds; it is a Chaos Engine fault scenario.
- **Grid hierarchy** — the topology an `Asset` sits within: `Substation` → `Feeder` → `NeighborhoodTransformer` → `Premise` (a primary-service premise hangs directly off its feeder). Owned by GridTopology. Nodes carry rated capacity (kVA) and nominal voltage; unknown capacity never means "unconstrained." Parent links record the **normal configuration**, not the currently energized path; code that needs an asset's constraining nodes asks GridTopology (`GetConstraintPath`) rather than walking parent IDs. Dispatch must respect node ratings — substation and neighborhood transformer, not just fleet-wide totals.
- **Grid node / `grid_node_id`** — any substation, feeder, neighborhood transformer, premise, or microgrid. Each keeps its own table and id, and also has a `grid_node_id` from the `topology.grid_nodes` registry: one id space across levels, assigned on insert, never changed, and kept after the node is removed. Node-keyed data (operating envelopes, node measurements, a future electrical network model) uses it. In code, `GridNode` is a module-internal abstract base class for these entities, not EF Core inheritance.
- **TechnologyType / ProtocolMapping** — `TechnologyType` is the internal technology classification of an asset component (`bess`, `solar_pv`, `wind`, `evse`) — technology only, never customer segment or size. `ProtocolMapping` maps a technology type to external protocol codes (OpenADR, IEEE 2030.5) so the mapping lives in data rather than application code. Both are owned by GridTopology; other modules resolve mappings through its contract. They are separate tables so internal and external taxonomies can evolve independently.
- **InterconnectionType** — an asset's position relative to the customer meter: `btm` (behind), `ftm` (in front), `atm` (across). Only premise-connected assets can be any of the three; feeder- and substation-connected assets are always `ftm`. Voltage level comes from the connection node, islanding is a premise/microgrid capability plus runtime state, and virtual metering is a program-enrollment arrangement — none of these are interconnection types.
- **Simulation run** — one execution of a simulator scenario, recorded in the Simulation module's run ledger (`simulation_runs`) with a run kind (`chaos` today; forecast, what-if, and replay are reserved for a digital twin), a lifecycle status, an append-only event history (`simulation_run_events`), and per-run overrides of each asset's starting state (`simulation_asset_states`). A run starts from a synthetic state, or from measured state at `initial_state_as_of`. Telemetry produced during a run is stamped with its `simulation_run_id`.
- **Run scope** — the part of the grid a run covers (a root node such as a substation or neighborhood transformer), the level of detail it loads (hierarchy, assets, or assets with components), and the topology version it uses (`topology_as_of`). Different runs are different views of the one topology, not separate topologies.
- **System-versioned table** — a table whose every previous row version is kept in a `<table>_history` twin with its validity period, so the table can be read as it was at any moment (`<table>_as_of`). Used for state that gets edited, such as topology. Set up by `topology.enable_versioning(<table>)`, which is re-run after any change to the table's columns.
- **Actor** — whoever made a change: a `user`, a `service` (e.g. the Chaos Engine), or the `system`. Identified by a UUIDv7 and recorded with each change and event.
- **Outbox** — a module's table of integration events, written in the same transaction as the change they describe and delivered by a background publisher, so events are never lost.
- **Shared kernel** — `Rva.SharedKernel`: the typed IDs, units, reference codes, and `Result` types every module shares. It contains no entities.
- **Module contracts** — each module's `.Contracts` project: the query interfaces, snapshot records, and integration events other modules may use.
- **Commanded state vs. Actual telemetry** — the state the core told a device to reach, vs. what the device is actually reporting. The gap between them is the variance calculated by the Reconciliation Loop.
- **Reconciliation Loop** — background service continuously comparing commanded state to actual telemetry and calculating variance; implemented as a Saga.
- **Deadman's Switch** — edge-local fallback logic so devices behave safely if communications with the core are lost.
- **Operator vs. Auditor (RBAC roles)** — Operator has control access; Auditor has monitoring/read-only access to the audit trail.
- **AI Sidecar / "Consultant, not the Decision Maker"** — the Python forecasting service; see `.ai/rules/python-sidecar.md`.
- **Chaos Engine** — the Monte Carlo fault-injection simulator (`src/Rva.Simulator`, a separate process) simulating thermal, voltage, and comms failures across the device fleet.
